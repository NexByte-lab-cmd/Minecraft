---

This skill guides creation of distinctive, production-grade frontend interfaces that avoid generic "AI slop" aesthetics. Implement real working code with exceptional attention to aesthetic details and creative choices.

The user provides frontend requirements: a component, page, application, or interface to build. They may include context about the purpose, audience, or technical constraints.

## Design Thinking

Before coding, understand the context and commit to a BOLD aesthetic direction:
- **Purpose**: What problem does this interface solve? Who uses it?
- **Tone**: Pick an extreme: brutally minimal, maximalist chaos, retro-futuristic, organic/natural, luxury/refined, playful/toy-like, editorial/magazine, brutalist/raw, art deco/geometric, soft/pastel, industrial/utilitarian, etc. There are so many flavors to choose from. Use these for inspiration but design one that is true to the aesthetic direction.
- **Constraints**: Technical requirements (framework, performance, accessibility).
- **Differentiation**: What makes this UNFORGETTABLE? What's the one thing someone will remember?

**CRITICAL**: Choose a clear conceptual direction and execute it with precision. Bold maximalism and refined minimalism both work - the key is intentionality, not intensity.

Then implement working code (HTML/CSS/JS, React, Vue, etc.) that is:
- Production-grade and functional
- Visually striking and memorable
- Cohesive with a clear aesthetic point-of-view
- Meticulously refined in every detail

## Design Variance

Use these baseline values to drive design decisions. Adapt them dynamically based on what the user requests:

* **DESIGN_VARIANCE: 8** (1=Perfect Symmetry, 10=Artsy Chaos) - Controls layout asymmetry, grid-breaking, and spatial experimentation.
* **MOTION_INTENSITY: 6** (1=Static, 10=Cinematic) - Controls animation complexity, from hover states only to full choreographed sequences.
* **VISUAL_DENSITY: 4** (1=Art Gallery/Airy, 10=Cockpit/Packed Data) - Controls spacing, whitespace, and information density.

These are defaults, not fixed rules. A luxury brand landing page might use (6, 4, 2) while a data dashboard could use (3, 5, 9). Let the context drive the values.

## Frontend Aesthetics Guidelines

Focus on:
- **Typography**: Choose fonts that are beautiful, unique, and interesting. Avoid generic fonts like Arial and Inter; opt instead for distinctive choices that elevate the frontend's aesthetics; unexpected, characterful font choices. Pair a distinctive display font with a refined body font.
- **Color & Theme**: Commit to a cohesive aesthetic. Use CSS variables for consistency. Dominant colors with sharp accents outperform timid, evenly-distributed palettes. Stick to one palette for the entire output, do not fluctuate between warm and cool tones within the same project.
- **Motion**: Use animations for effects and micro-interactions. Prioritize CSS-only solutions for HTML. Use Motion library for React when available. Lifecycle: scale to zero
This is the most important mental model for building correctly:

After 5 minutes with no requests, the server is shut down. The next request starts a fresh process (a cold start).
All process memory is lost on every scale-to-zero, deploy, and platform maintenance event. In-memory caches are fine as caches; they are NEVER storage. Anything that must survive belongs in Netlify Blobs or Netlify Database (see the general-database skill to choose).
Netlify can run several instances of the server at once (up to 3; 1 on Free and Personal plans). Each has its own memory and its own WebSocket connections; nothing in memory is shared between them.
In-flight requests and open WebSocket or Server-Sent Events connections are never cut off by the idle shutdown; while any are open, the instance stays running.
The server must send a response's status and headers within 20 seconds, or the request fails with a 502. Stream slow responses, such as AI output, or respond right away and finish with waitUntil.
Background work that outlives the request that triggered it (for example, responding early and then finishing a task) MUST be registered with getContext().waitUntil(promise). Registered work keeps the process alive until the promise settles; unregistered work may be reclaimed the moment no requests are active.
Never keep the server alive on purpose: no self-pings, no timer that calls the server, no waitUntil chain that schedules more work to stay running, and no scale.min above 0 (during Early Access a deploy that sets it fails). Scale to zero is the design. If the user asks for an always-on server, explain this and build without it.
Scheduled or recurring work (cron, nightly cleanup, periodic sync) goes in a scheduled function (see the netlify-functions skill) that calls a server route. Never use setInterval or other timers meant to outlive a request.
waitUntil extends the idle lifetime, but deploys and platform maintenance still stop the process with only a short grace window. Keep background tasks short (seconds, not minutes), and persist anything critical before responding. For genuinely long jobs, call a background function from the server (see the netlify-functions skill), or persist a job record and process it in resumable increments across requests.
Graceful shutdown hook (optional): register it with onShutdown from @netlify/server. It runs as soon as the instance starts stopping and receives drained, a promise that resolves once in-flight requests and waitUntil work have finished. Stop background work and close WebSockets right away, then await drained before releasing what that work still uses. Apps that already listen for SIGTERM keep working.

  wss.close()
  await drained
  await pool.end()

Rules:

ONLY call getContext() while handling a request (inside a route handler, middleware, or code awaited from one). It throws outside a request.
Works with every server form, including WebSocket upgrade handling.
Anything started inside a request (a setInterval, a lazily started background loop, a client that creates its own timers, WebSocket message handlers) keeps that request's context for its whole life, so getContext() there returns a stale request instead of throwing. Start long-lived work outside request handling, and never read per-request context from it.
SSO user: context.user
On private projects and sites protected by Netlify team login, the context also carries the user who signed in through Netlify's SSO: context.user with id, email, and expiresAt (a Date). It is undefined when the request didn't come from such a user. Netlify verifies the visitor and sets it itself, so it can't be spoofed with request headers. This is the Netlify team member viewing the site, not a Netlify Identity user.
